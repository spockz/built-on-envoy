# Extensions Directory

This directory will contain community-contributed Envoy extensions.

## Structure

Each extension should be in its own directory with:

```
extension-name/
├── README.md            # Description and usage
├── manifest.yaml        # Metadata (name, version, author, etc.)
├── {go,lua,rs}          # Extension code (language-specific)
└── config.schema.json   # (Optional) JSON schema describing the extension configuration
```

## Extension e2e tests

Extension e2e tests live in the [tests/e2e](./tests/e2e) directory. Take a look at the README file
there for details on writing end-to-end tests for your extension.

## Executable manifest examples

Manifest examples can keep a hand-written `code` snippet, or define `config` and `commands` so
the snippet is generated by running the extension. Use a `config` object for executable
examples; `{}` is valid when the extension needs no settings. Commands are argument arrays and
run directly without a shell. Each command runs in order, and `expectedExit` defaults to `0`.
An HTTP denial response does not make `curl` fail unless the command uses a flag such as
`--fail-with-body`.

The generator expands `${PROXY_URL}`, `${ADMIN_URL}`, `${UPSTREAM_ADDRESS}`, and `${WORK_DIR}`
in arguments and configuration strings. It copies the extension's `examples/` fixtures into a
temporary work directory before starting Envoy; use paths relative to that fixture directory in
commands. It serves a local
upstream at `127.0.0.1:10001` by default and uses Envoy `1.38.0` unless another version is passed.
Envoy downloads are cached in the ignored `extensions/out/example-envoy-cache/` directory;
extension binaries and runtime state remain isolated for each generation.

Generated `code` is updated only after every selected manifest and command succeeds. The check
mode runs the same examples and compares generated snippets without writing files. Captured
values stay in the transcript, with line endings recorded explicitly. Volatility rules affect
comparison only, so spacing, units, and numeric precision
remain significant. HTTP `Date` headers are handled automatically. Declare other changing response
headers by listing their names in `volatileHeaders`. The generator infers date or duration format
from each value. Duration values may be bare numbers or include units. Both values must have the
same recognized type and format; unrecognized values compare exactly. Declaring a numeric header
also makes changing counts or IDs volatile, so list only values whose changes should be ignored.
For volatile values in response text, use a
`comparison` rule with `type: date` or `duration` and a response-only Go regexp containing exactly
one named `(?P<value>...)` capture.

For example, a filter that returns a varying latency header can declare:

```yaml
config: {}
commands:
  - argv: [curl, --silent, --show-error, --include, "${PROXY_URL}/status/200"]
volatileHeaders:
  - x-fault-inserted-latency
```

These fields belong to an entry in `examples`, alongside `title` and `description`. Leave out
`code` for a new executable example; `update-examples` adds it. A changed volatile value keeps
the existing transcript, while a changed value format or other output produces a diff.

Run the tool from the repository root through the extension Makefile entrypoint, setting
`EXTENSION_PATH` to the extension directory:

```sh
make -C extensions update-examples EXTENSION_PATH=example-wasm-go
make -C extensions check EXTENSION_PATH=example-wasm-go
make -C extensions check-examples EXTENSION_PATH=example-wasm-go
make -C extensions test-examples EXTENSION_PATH=example-wasm-go
```

`check` depends on the separate `check-examples` target, which can also be run directly.

Composer is a bundle, so its entrypoint includes the root manifest and every directory in
`PLUGIN_DIRS`, including the built-in `goplugin-loader` manifest:

```sh
make -C extensions update-examples EXTENSION_PATH=composer
make -C extensions check EXTENSION_PATH=composer EXAMPLES_ARGS="-envoy-version 1.38.0"
```

Pass generator options through `EXAMPLES_ARGS`, for example `-boe /path/to/boe`,
`-envoy-version 1.39.0`, `-envoy-path /path/to/envoy`, `-timeout 2m`, or
`-upstream-address 127.0.0.1:10001`. Add `-check` only through the
`check-examples` target; it prevents generated snippets from being written.

The generator's [requirements and invariants](../cli/tools/gen-examples/README.md) describe
execution, comparison, and manifest update guarantees.

## Contributing an Extension

1. Fork this repository
2. Create a new directory under `extensions/` with your extension name
3. Add all required files (see structure above)
4. Ensure your README includes:
   - Description of what the extension does
   - Installation/usage instructions
   - Configuration options
   - Examples
5. Open a pull request

## Extension Guidelines

- Extensions should be focused on a single responsibility
- Include comprehensive documentation
- Provide working examples
- Follow Envoy best practices
- Include tests where applicable
